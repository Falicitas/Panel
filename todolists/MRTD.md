# ~

MRTD 要解决的事：给一台 TD 刚启动时被装进内存的初始内容做一个定长值，让远处的人凭这个值确认装进去的是什么，且这份内容改一个字节、这个值就跟着变。

先看被测的东西是什么。TD 的初始内存是 VMM 一页一页装进去的——装哪一页、装到哪个物理地址（GPA）、按什么顺序。同样的字节装到不同 GPA，算不同的初始状态。所以这个定长值要同时盖住"装了什么内容"和"装到哪个地址"。

定长、且改一字节必变，这步逼出密码学 hash，TDX 用 SHA384。跟你把几百 MB 的 rootfs 压成一个 hash 是同一件事。

难处在被测的是"一连串装页动作"，不是一块现成数据。把一连串动作压成一个 hash，有两种自然写法，你先停一下想想区别——

写法一：每装一页，把当前的 48 字节和这页的摘要拼起来哈一次，得到新的 48 字节，再喂给下一步。值始终 48 字节，一步接一步。

写法二：把每个装页动作描述成一段字节，全部按顺序接成一条长流，从头到尾只哈一次。

RTMR 用的是写法一（fold 链），你一直拿它套 MRTD，所以拧着了。MRTD 用的是写法二。这是 Intel 的设计选择，两个寄存器各用一种，没谁被逼。

>   ## 目标
>
>   VMM 要往一台空的 TD 里，按某个清单，把固件镜像（OVMF/TDVF）的每一块搬进 TD 的内存。问题是搬哪些块、各搬到哪个地址、哪些块要量内容——VMM 怎么知道？
>
>   它不能瞎搬。搬错一个字节、搬错一个地址，MRTD 就变，attestation 就对不上。所以必须有一份**精确到地址的搬运清单**。这份清单，就是下面要推的所有词的来源。
>
>   ## 第一个被逼出来的东西：metadata
>
>   固件镜像是一个几 MB 的文件（你的 `OVMF.fd` 之类）。VMM 把它整个搬进 TD 内存就完事了吗？不行，有两个问题：
>
>   一，这个文件内部不是铁板一块。它里面有好几个功能不同的区域：放固件代码的、放配置变量的、要预留给运行时用的空白内存。这些区域，搬进 TD 之后该放到哪个物理地址，各不相同，不能一股脑顺序铺。
>
>   二，不是每块都要量内容。固件代码必须量（它决定 TD 跑的是什么），但有些区域只需要"占住这个地址"，内容是空的或者运行时才填，量它没意义。
>
>   所以 VMM 需要一张表，告诉它：这个文件要切成哪几块、每块搬到哪个 GPA、每块量不量内容。这张表就嵌在固件镜像文件里，叫 **metadata**——固件构建时由固件自己写进去的一段描述符。VMM 开机时先去文件里找到这张表，照着搬。
>
>   metadata 不是 VMM 发明的，是固件作者写好放在镜像里给 VMM 看的"搬运说明书"。
>
>   ## 第二个：段（section）
>
>   metadata 这张表里的每一行，描述文件里的一块怎么搬。一行就是一个 **section**（段）。一行记三件事：
>
>   -   这块在固件文件里从哪个偏移开始、多长；
>   -   搬进 TD 后落在哪个 GPA；
>   -   一个标志位：要不要 MR_EXTEND（要不要量内容）。
>
>   你那台机器的表，第 0 行第 1 行长这样：
>
>   ```
>   段号  类型      文件来源        目标 GPA      MR_EXTEND
>   0     BFV       <固件代码区>    0xffc84000    有
>   1     CFV       <配置变量区>    0xffc00000    无
>   ...   TempMem   <无，纯占位>    0x800000 带   无
>   ...   TD_HOB    <无，纯占位>    0x800000 带   无
>   ```
>
>   所以"第 0 段是 BFV、起始 GPA 0xffc84000、带 MR_EXTEND"这句话，逐字翻译就是：**表的第 0 行，描述的是固件代码区，要把它搬到物理地址 0xffc84000 这一片，并且要逐块量它的内容。**
>
>   ## 第三个：这几个段的类型各是什么
>
>   四个名字，对应固件文件里四种功能不同的区域：
>
>   **BFV**（Boot Firmware Volume）。固件的代码本体——TD 一上电执行的那段程序就在这里。它决定了 TD 跑的是什么，所以**必须量内容**（MR_EXTEND = 有）。它占了大头，892 页。
>
>   **CFV**（Configuration Firmware Volume）。固件的配置变量区，存的是一些设置项（比如安全启动用的密钥库）。它的内容**不进 MRTD**（MR_EXTEND = 无）——因为它在不同部署里可能不一样，但不影响"跑的是哪份固件代码"这件事，量它反而让 MRTD 不稳定。所以只在流里记一笔"0xffc00000 这片装了 64 页"，不记内容。
>
>   **TempMem**（Temporary Memory）。固件早期临时用的一块内存（栈、堆之类）。开机这一刻它是**空白的**，没内容可量。metadata 里有它这一行，只是为了让 VMM "把这片地址先占住、标成已分配"。所以只记 GPA、不量内容。
>
>   **TD_HOB**（Hand-Off Block）。VMM 留给固件的一张小纸条，写着"这台 TD 有多少内存、CPU 几个"这类信息，固件启动后读它来认识自己。它的内容是 VMM 运行时才填的，build 这一刻也是**占位**，只记 GPA。
>
>   后三个的 GPA 都在 0x800000（8 MB）一带，是因为这是低地址的常规 RAM 区，临时内存和交接块按惯例放低处；BFV/CFV 的 GPA 在 0xffc00000（接近 4 GB 顶）一带，是因为固件代码按 x86 惯例映射在地址空间最顶上（复位向量 0xfffffff0 就在那附近）。这两个地址区的选择是固件/平台约定，不是被推出来的。
>
>   ## 第四个：VMM
>
>   到这你应该能自己说出 VMM 是谁了。**VMM = Virtual Machine Monitor**，就是宿主机上那个负责创建和喂养这台 TD 的程序（在阿里云这层是 QEMU + KVM 那套）。
>
>   它在 TD build 期间干的活，就是：打开固件镜像 → 读出里面的 metadata 表 → 一行一行照着搬：BFV 那行带 EXTEND，就发 PAGE.ADD 再发 16 次 MR.EXTEND；CFV/TempMem/TD_HOB 那几行不带，就只发 PAGE.ADD。每发一个动作，TDX 模块就往那条 SHA384 流里追加对应的字节（这是你上一版已经搞清楚的部分）。八行全搬完，发 FINALIZE。
>
>   所以整条因果链是：**固件作者写 metadata（说明书）→ VMM 读说明书 → 按说明书逐段发搬运动作 → 每个动作被 TDX 模块记进 SHA384 流 → finalize 出 MRTD。** MRTD 之所以能代表"装了什么"，正是因为 VMM 的每一步都被 metadata 钉死、且每一步都进了流。
>
>   ## 一句话回填你那五个片段
>
>   -   「metadata 里第 0 段是 BFV，起始 GPA 0xffc84000，带 MR_EXTEND」= 搬运说明书第 0 行：把固件代码区搬到 0xffc84000，要量内容。
>   -   「第 1 段是 CFV，不带」= 第 1 行：把配置变量区搬到 0xffc00000，只占地址不量内容。
>   -   「VMM 从第 0 段第一页开始」= 宿主机那个喂 TD 的程序，照说明书从第一行第一页动手。
>   -   「走完 BFV，轮到 CFV，CFV 不带 MR_EXTEND，每页只追加装页段」= 代码区搬完搬配置区，配置区只发 PAGE.ADD 不发 EXTEND，所以流里只有它的 GPA、没有它的内容。
>   -   「再往后 TempMem、TD_HOB，GPA 在 0x800000 一带，不带内容」= 后面两行是纯占位的内存区，地址在低位 RAM，build 时是空的，只记地址。

写法二具体怎么走。TDX 模块在 build 期间只开着一个 SHA384（`sha384()`，全程不 finalize）。VMM 每做一个动作，就往这个 hash 里追加一段固定格式的字节，段与段首尾相接、中间没有分隔符。整条流这么一段段长出来，最后哈一次。

拿我们这台的真实数据走一遍。metadata 里第 0 段是 BFV，起始 GPA `0xffc84000`，带 MR_EXTEND；第 1 段是 CFV，起始 GPA `0xffc00000`，不带。VMM 从第 0 段第一页开始。

第一步，把 BFV 第一页装进去（GPA `0xffc84000`）。往流里追加 128 字节：

```
字节 0–11 : 4D 45 4D 2E 50 41 47 45 2E 41 44 44   "MEM.PAGE.ADD"
字节 12–15: 00 00 00 00                            补到第 16 字节
字节 16–23: 00 40 C8 FF 00 00 00 00                GPA 0xffc84000，小端
字节 24–127: 00 …                                  余下全 0，整段共 128 字节
```

这一段只写了"这页装在 `0xffc84000`"，没写这页的内容。

第二步，量这一页的内容。一页 4K，切成 16 个 256 字节的块，一块一块量。第 1 块（GPA 仍是 `0xffc84000`）追加 128 字节头，紧跟 256 字节内容：

```
头 128 字节：
  字节 0–8  : 4D 52 2E 45 58 54 45 4E 44   "MR.EXTEND"
  字节 9–15 : 00 00 00 00 00 00 00          补到第 16 字节
  字节 16–23: 00 40 C8 FF 00 00 00 00       GPA 0xffc84000，小端
  字节 24–127: 00 …                          余下全 0
紧跟 256 字节：
  <BFV 文件偏移 0x84000 起的那 256 字节，原样拷进流>
```

第 2 块，GPA 是 `0xffc84000 + 0x100 = 0xffc84100`，同样 128 字节头 + 256 字节内容：

```
  4D 52 2E 45 58 54 45 4E 44
  00 00 00 00 00 00 00
  00 41 C8 FF 00 00 00 00       GPA 0xffc84100（注意第 2 个字节从 40 变 41）
  00 …
紧跟 256 字节：<BFV 偏移 0x84100 起的内容>
```

一直量到第 16 块（GPA `0xffc84f00`）。这一页就完了：1 个装页段 + 16 个量内容段，往流里写了 128 + 16×(128+256) = 6272 字节。

第二页 GPA `0xffc85000`，重复同样的 1 + 16 段，GPA 每页加 `0x1000`。BFV 一共 892 页，全这么走完，光 BFV 就往流里写了约 5.6 MB。

走完 BFV，轮到第 1 段 CFV。CFV 不带 MR_EXTEND，所以它每一页只追加装页段、不追加内容：

```
  4D 45 4D 2E 50 41 47 45 2E 41 44 44   "MEM.PAGE.ADD"
  00 00 00 00
  00 00 C0 FF 00 00 00 00               GPA 0xffc00000
  00 …
```

CFV 64 页，就是 64 个这样的 128 字节段，GPA 从 `0xffc00000` 每页加 `0x1000`，中间一个内容字节都没有。所以 CFV 的内容进不进 MRTD——不进，流里只有它的 GPA。

再往后是 TempMem、TD_HOB 那几段，同样只追加装页段（GPA 在 `0x800000` 一带），不带内容。

8 段全部走完，VMM 收尾，对这条几 MB 长的流做唯一一次 finalize，吐出 48 字节，就是 MRTD，然后锁死。

这三个动作的名字：装一页叫 `TDH.MEM.PAGE.ADD`，量一个 256 字节块叫 `TDH.MR.EXTEND`，收尾叫 `TDH.MR.FINALIZE`。

>   #### 先记一件事：build 期间有两样东西在同时被填
>
>   一样是 **TD 的物理内存**——那片要被装进固件、最后 TD 要在上面跑起来的真实内存。 一样是 **那条 SHA384 流**——TDX 模块攥着的、最后 finalize 出 MRTD 的字节流。
>
>   VMM 发的每个动作，要么往内存里搬数据，要么往流里追字节，或者两者都干一点。两个动作的区别就在这：它们各自动哪样、动多少。
>
>   #### TDH.MEM.PAGE.ADD —— 搬一页进内存
>
>   这个动作的主语是"搬运"。VMM 说：把固件文件里这 4KB，搬到 TD 物理内存的 GPA `0xffc84000` 去。
>
>   它干两件事：
>
>   1.  **往 TD 内存里**真的写进去 4096 字节（这一页的内容，从固件文件拷过来）。
>   2.  **往 SHA384 流里**追加 128 字节——`MEM.PAGE.ADD` + 这页的 GPA + 补零。
>
>   注意第 2 件：进流的 128 字节里**只有 GPA，没有那 4096 字节内容**。也就是说，PAGE.ADD 把页内容搬进了内存，但没把页内容记进流。流只知道"`0xffc84000` 这个地址装了一页"，不知道这页里是什么。
>
>   **粒度：一页一次。** 一页 4KB，一个 PAGE.ADD 搞定。892 页就发 892 次 PAGE.ADD。
>
>   #### TDH.MR.EXTEND —— 把内存里某 256 字节，记进流
>
>   这个动作的主语是"记账"。它**不往内存搬任何东西**——内存里那一页，PAGE.ADD 已经搬好了。EXTEND 干的是：把已经躺在内存里的某 256 字节，抄进 SHA384 流。
>
>   它只干一件事，往流里追加：
>
>   1.  128 字节头（`MR.EXTEND` + 这 256 字节块的 GPA + 补零），
>   2.  紧跟着那 **256 字节内容本身**。
>
>   这一步才是把"页里是什么"记进流的动作。PAGE.ADD 记了地址，EXTEND 记内容。
>
>   **粒度：256 字节一次。** 这就是你一直没分清的关键——EXTEND 的单位不是页，是 256 字节的块。一页 4KB = 16 个 256 字节块，所以量完一整页要发 **16 次** EXTEND，GPA 一次加 `0x100`。

所以 `MRTD = SHA384(所有这些追加的字节，按 VMM 发出动作的顺序，接成的一条流)`。中间没有"出 48 字节再喂回去"，只有末尾那一次 finalize。

PAGE.ADD 只把 GPA 写进流，不写页内容；内容是靠 MR.EXTEND 写进去的。所以一页量不量内容，看 VMM 给它做不做 MR.EXTEND。

到这里就能回答你那句"哈希唯一为什么还能不同"，连带"手里有固件为什么还原不出来"。

把 MRTD 分两层：怎么哈，和哈什么。

怎么哈——SHA384 这个函数、加上每段记录的格式（`MEM.PAGE.ADD`+GPA 那个模板）——是 Intel 模块写死的，VMM 碰不到。这层确实唯一。

哈什么——那条字节流——是 VMM 拼出来的。VMM 是个程序，它决定往流里追加哪些段：

-   哪些页、装到哪些 GPA（GPA 直接写进 PAGE.ADD 段，同样内容换个地址，段就变）
-   顺序（SHA384 认顺序，先 BFV 还是先 CFV，流就不同）
-   每页量不量内容（做不做 MR.EXTEND）
-   要不要装固件里根本没有的页——VMM 能自己造一段内容装进去、也量进去（厂商 config、GCE 那种 LaunchOptions）

固件二进制给的是每页的内容。它不告诉你 VMM 这个程序怎么拼这条流。

标准 VMM（QEMU）拼流的规则，就是严格照固件里那张 TDVF metadata 表：表里列了哪几段、各自 GPA、各自量不量。所以标准情况下光有固件就够——照表把流重拼一遍、哈一次，就得出 MRTD。我那套 Python 算出来的 `ad29a052` 就是这么来的。

阿里云说他们的加载流程跟社区不同。在"怎么哈"和"metadata 表"都已经验过是标准的之后，这句话能落地的地方，只剩"哈什么"那条流被拼得不一样：换了顺序，或者多塞了固件里没有的段。

最难办的是多塞段这种。假设 VMM 往流中间塞了一段它自己造的内容，这段和别的字节一起被哈进去了。SHA384 单向，你拿到最终的 `e0199499`，反推不出中间那段是什么。于是这时候：固件二进制不够，那段不在固件里；固件加最终 MRTD 值也不够，单向函数解不出那段；只有阿里云把那段内容直接给你，或者直接告诉你这版固件该出的 MRTD 值。

回到我们卡的地方。我们按标准规则拼流，算出 `ad29a052`；真机 finalize 出的是 `e0199499`。两者不等，只剩两种可能：要么我们喂进流的页内容就不对（BFV 是运行期 dump 的，可能被固件自己改过），要么阿里云拼的流不是标准那条（换了序，或塞了段）。前者拿到纯净固件能解决；后者要是塞了段，固件给得再全也算不出来。
