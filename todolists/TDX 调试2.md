## 目标

一句话：在一台我不拥有、也不信任的公有云机器上，运行一份我指定的代码，并且能向远处的人证明——这台机器此刻跑的就是这份代码，没被换过。

这句话里有两个独立的硬要求，拆开看，整个架构是从它们身上长出来的：

- 要求一，运行我指定的代码：代码的内容得被钉死，不能被人在我背后换掉，而且运行期间也不能被换。
- 要求二，能证明：得有别人伪造不了的证据，证据还能传到远处去验。

先追要求二，因为它决定了要求一该用什么形式去满足。

## 证明需要什么，反推出"代码必须先变成一个 hash"

"伪造不了"意味着证据的信任根不能是软件——软件能被篡改，云厂商对你的虚拟机有完全的物理访问。信任根只能落在一个连云厂商都改不动的地方。TDX 提供的就是这个东西：CPU 内部有一段逻辑，把"这台机器启动时到底加载了什么"测量进几个寄存器（MRTD、RTMR），再用一把只有 Intel 芯片自己持有的私钥，把这些测量值签成一份 quote。远处的人拿到 quote，一路验签到 Intel 的根 CA，就能确信：这串测量值确实出自一颗真的 TDX 芯片，中途没被人改。

那么"证明我跑的是指定代码"，就等于把这份代码以某种方式喂进这些测量寄存器，再产出 quote。

但这里有个物理限制：测量寄存器就是几个定长的 hash 槽，几十个字节，装不下一个几百 MB 的 rootfs。于是被迫做一件事——把整份代码压成一个定长指纹，只测量这个指纹。指纹得满足一个性质：代码改一个字节，指纹必变；指纹没变，代码就一定一字未改。这正是密码学 hash 的定义。

到这一步，两个要求接上了头：钉死代码 = 算出它的 hash 并测量这个 hash；验证 = 比对 hash。代码本身不进寄存器，它的 hash 进。

## 钉死代码不能只在启动时算一次，于是被迫用 hash 树

现在追要求一。最朴素的做法是：启动时把整盘读一遍，算个 hash，测量它。但这不够，漏了"运行期间"。

<u>代码要从磁盘读。如果磁盘内容在运行中途被改了（云厂商有这个能力），启动时算的那个 hash 保不了运行时读到的数据。所以真正需要的是：运行期间每一次从磁盘读数据，都能当场验证"这块数据属于我启动时测量的那一份"。</u>

这就把"整盘一个 hash"否决了。你不可能每读一个 4KB 块就把整盘重新 hash 一遍，那样系统慢到没法用。需要的是局部可验证——读哪一块，只校验哪一块的代价，但仍然能追溯到同一个总指纹。

满足这个条件的数据结构是 Merkle 树（hash 树）：每个数据块先算自己的 hash，这些 hash 再两两往上 hash，层层收敛，最后汇成一个 root hash。读某一个块时，只需要沿着它到树根的那条路径，校验 log (n) 个 hash 就够，不用碰其它块。而那一个 root hash，锁住了整棵树、锁住了每一个块——任何一块被改，它的 hash 变，沿路一直传到根，root hash 必变。

<u>Linux 内核里实现这套机制的是 dm-verity。它有个前提：底层数据必须只读。道理很直接——如果数据能被合法地写，hash 就得跟着变，那"root hash 钉死内容"这件事就不成立了。所以底层用一个只读文件系统，选的是 erofs。</u>

于是要求一的形态被完全推定了：代码打包成只读的 erofs，在它上面用 dm-verity 建 hash 树，得到一个 root hash。这个 root hash，就是上一节说的、要被测量的那个指纹。两条线在 root hash 这一点合流。

## root hash 要起作用，就得有人在启动早期告诉内核——而那个"人"不可能是 rootfs 自己

<u>光有 root hash 不够，得让系统真的按它来挂载和校验。具体说，启动时必须有人告诉内核："根文件系统是个 dm-verity 设备，数据在这块盘，hash 在那块盘，root hash 是这个值。"内核拿到这些，才能建起 `/dev/mapper/root` 这个经过校验的块设备，挂成根。</u>

<u>问题是，这件事发生在根还没挂的时候。谁来做、在哪个环境里做？</u>

<u>这里值得你先停一下自己想：既然根（`/`）还没挂上，那挂根这个动作，是哪个正在运行的程序发出的？它住在哪个文件系统里？</u>

<u>答案逼出了 initrd 的存在，而且是逻辑上逼出来的，不是工程上图方便。推导是这样：</u>

要把 erofs 挂成 `/`，得先有一个已经在运行的 Linux 来执行"挂载"这个动作，执行挂载得用到 `mount`、`veritysetup` 这些程序。但这些程序住在哪？如果住在那个还没挂上的真根里，就出现一个回环——挂根需要根里的工具，可工具要等根挂上了才够得着。鸡和蛋。

破这个环，唯一的办法是：先用一个临时的、自带工具的小型根系统把机器启动起来，在这个临时系统里把真根校验好、挂好，然后切换过去。这个临时小系统就是 initrd。

所以 initrd 不是一个可选的优化，是"要挂载一个本身需要工具才能挂载的根"这个任务的前置条件。它必须自带三样东西：dm-verity 内核模块（提供校验能力）、erofs 模块（让内核认识 erofs）、veritysetup（下令建 verity 设备）。这三样放进真根里没有意义，因为用到它们的那一刻，真根还没挂上，够不着。这一句话也解释了你之前的疑问"为什么 verity 是 initrd 干的"——它没得选，只能在 initrd 里干。

切换那一下叫 switch-root。它有个后果，后面会用到：initrd 是个临时系统，真根挂好、切过去之后，initrd 连同它里面跑着的所有服务一起退场，真根是一套全新启动的 systemd。记住这一点。

## initrd 怎么知道参数：为什么 cmdline 里有那一串，以及为什么 root hash 一变你就得改它

initrd 要校验真根，得知道三个参数：哪块盘是数据、哪块盘是 hash、root hash 是多少。这些从哪来？

两个选项。一是写死进 initrd。二是从外部传进来。

写死的问题在于：root hash 是个易变量——代码每改一次它就变一次；而 initrd 里那些模块和工具是不变的。把一个天天变的参数，焊死进一个本该不变的 initrd，意味着每次改代码都得重造 initrd，不划算。

<u>所以参数走外部传入。内核启动时，能从外部捎带一串文本进来的通道，就是 kernel command line（cmdline）。bootloader 把 cmdline 连内核一起加载进来，内核把它放进 `/proc/cmdline`，initrd 里的 init 程序读它。</u>

>   cmdline 的控制：具体到机器，这串文本的源头是 `/etc/grub.d/40_custom` 里那行 `linux /boot/vmlinuz-... systemd.verity=1 roothash=... `。`update-grub` 把 `40_custom` 编译进 `/boot/grub/grub.cfg`，grub 启动时读 grub.cfg 里的 `linux` 那行，把内核路径后面那串原样交给内核。grub 一个字都不改，它只负责把写在配置里的东西传过去。

这就是你 deploy 时反复看到的那一串的来历：

```
systemd.verity=1
roothash=<root hash>
systemd.verity_root_data=<数据盘 by-id>
systemd.verity_root_hash=<hash 盘 by-id>
```

它们不是配置文件，是"外部传给 initrd 的运行参数"。也由此能解释你脚本里那个同步动作：每次 erofs 内容变了，root hash 跟着变，你必须同步把 cmdline 里的 `roothash=` 改成新值。否则 initrd 拿着旧 hash 去校验新盘，对不上，verity 建不起来，启动失败。参数和被校验的对象必须配套。

## 内核和 initrd 自己谁来担保：measured boot 链，以及它为什么决定"只能换三样"

现在你有了内核 + initrd（负责校验挂载真根） + 只读 erofs 真根。但内核和 initrd 自己也是代码，凭什么相信它们没被换？

这靠 measured boot 的链式结构：每一环在把控制权交给下一环之前，先测量下一环，把测量值 extend 进 RTMR。一环测一环，环环相扣。固件测量它加载的内核和 initrd；cmdline 里的 root hash 也在测量范围内，加上 dm-verity 运行时持续保证真根匹配这个 hash。最后 quote 把整条链的测量结果一起签出来。

链得有个起点，起点必须是改不了的。在公有云上，这个不可改的前缀是云厂商给定的：固件 TDVF、它后面的 shim、再后面的 grub，都是阿里云签好、固定的，你动不了——你一改，MRTD 或 RTMR0 就跟厂商的已知基线对不上，远处验证直接失败。

你能接管的，是 grub 之后的部分：换上你自己的 kernel、你自己的 initrd、你自己的 rootfs。所以"能换的只有这三样"不是谁规定的限制，是 measured boot 链加上公有云固定前缀两个条件挤出来的结论——前缀既然钉死，你只能从能接管的那一环开始，让测量从那里一直延续到你的代码。

到这里，要求一和要求二的主干就完整了：系统能起来，真根被 dm-verity 锁在一个 root hash 上，这个 root hash 进了测量链，quote 能把它签出来给远处验。这就是整套架构的全部存在理由——没有一处是"碰巧这么设计"，每一处都是从那句话目标里被逼出来的。

## 第二条线：系统起来还得能用，于是需要网络，于是需要一整条没人能省的链

上面解决的是"可信地起来"。但一个起来了却连不上的机器没用——你要 SSH 进去量 RTMR2，要让 gateway 对外服务，这些都要网络。这条线是这次 debug 真正卡住的地方，也用同样的方式倒推一遍。

从终点往回推。最终要的是：用户态程序（sshd、gateway）能通过网卡收发 IP 包。要收发 IP 包，网卡得有个 IP 地址。地址要么静态配死，要么靠 DHCP 去网络上要。要发 DHCP，网卡得是 up 的、有载波、内核里得有它的驱动。而在这之前，网卡这个硬件得先被内核发现——在 PCI 总线上 probe 出设备，绑上驱动。

>   先破一个最可能卡住你的点:你这台是虚拟机,哪来的"硬件"和"驱动"?
>
>   虚拟机里的网卡不是一块真的金属卡,但对虚拟机内部的内核来说,它跟真硬件没区别,走的是同一套发现流程。底层是这样:跑你这台 TD 的物理母机上,hypervisor(KVM/QEMU 那一层)模拟出一个设备,让你的虚拟机"以为"自己插着一块网卡。这个模拟出来的设备遵循一个叫 virtio 的规范——一种专门为虚拟化设计的设备标准(模拟一块真实存在的 Intel 网卡也行,但 virtio 是为"我知道自己在虚拟机里"这个场景设计的,更高效)。所以你机器里的"网卡",准确说是一块 virtio 虚拟网卡。它的驱动叫 virtio_net,意思就是"会跟 virtio 这种虚拟网卡打交道的那段内核代码"。
>
>   理解了这点,我们正着把那条链走一遍。文档里那段是倒着写的(从"能收发包"往回推到"硬件被发现"),倒着写是第一性原理推导的需要,但你第一次理解一个物理过程,正着走更顺。
>
>   第一步,设备挂在 PCI 总线上。 PCI 总线你可以理解成计算机内部挂硬件的一套插槽系统——网卡、显卡、磁盘控制器,都挂在 PCI 上,每个占一个位置,有个地址。虚拟机也有一条(虚拟的)PCI 总线,virtio 网卡就挂在上面。你之前 debug 时,诊断盘里 eth0 那条指向 `pci0000:00/0000:00:07.0/virtio1/net/eth0`,<u>这串路径现在能读懂了:PCI 总线 `0000:00` 上 `07.0` 这个位置,挂着一个 virtio 设备,它下面是一块网卡,内核叫它 eth0。那串不是乱码,是这块网卡的"住址"。</u>
>
>   第二步,<u>内核开机时扫描 PCI 总线,把设备 probe 出来。</u> probe 就是"探测"——<u>内核启动时挨个 PCI 位置看过去,发现"07 号位置上有个东西",读出这个设备的身份编号(每个 PCI 设备都有一对 ID,标明它是谁家的、什么型号)</u>。virtio 设备的身份编号是固定的,内核一读就知道"这是个 virtio 网卡"。到这一步,内核只是知道了"这儿有这么个设备",还没法用它。
>
>   第三步,给设备绑上驱动。 内核知道有个设备还不够,它得有对应的驱动才会去操作这个设备。驱动是一段"专门会跟这种设备说话的代码":怎么给它发数据、怎么从它收数据、怎么问它状态,都写在驱动里。内核拿设备的身份编号去匹配——"virtio 网卡"这个身份对应 virtio_net 这个驱动,配上。这里就接到了你之前查 built-in 那件事:virtio_net 这段代码,可以编进内核本体(`CONFIG_VIRTIO_NET=y`,你的情况就是这样,所以它不以单独的 .ko 文件存在),也可以做成一个独立模块文件按需加载(`=m`)。不管哪种,绑定这一刻完成后,网卡才真正"能用",作为一个网络接口出现,有了 eth0 这个名字。
>
>   把前三步连起来:硬件挂在 PCI 上 → 内核扫描发现它 → 配上驱动。这三步走完,你才有一个能操作的网卡。在虚拟机里这三步全是内核干的,你这次没在这三步上出问题(virtio_net built-in 在内核里,设备也 probe 出来了,驱动也绑上了——诊断盘里 `eth0 driver = virtio_net` 就是证据)。
>
>   另外，虚拟网卡不是 rootfs 里的一个文件或配置,是母机那层 hypervisor 模拟给你这台虚拟机的硬件。它的存在由阿里云怎么创建这台 TD 实例决定,跟你 mkosi 构建什么 rootfs 完全无关。驱动是另一回事,它确实是软件、确实可能进 rootfs。但你的 virtio_net 是 built-in 编进内核本体的,不是 rootfs 里的独立模块文件。
>
>   >   如果 virtio_net 是 built-in(`=y`,你的情况):驱动在 vmlinuz 里,跟 rootfs 无关。rootfs 的 `/lib/modules` 里有没有它都不影响——你这次查到 rootfs 里没有 `virtio_net.ko`,正常,因为它根本不以文件形式存在,它在内核本体里。
>   >
>   >   如果 virtio_net 是独立模块(`=m`):那它就是 `/lib/modules/.../virtio_net.ko` 这么个文件,得在 rootfs 里。这种情况下 mkosi 构建时要是没把它打进模块树,启动就真的会缺驱动、网卡起不来。你这次因为是 built-in,躲过了这种可能。
>
>   第四步往后,是让这块能用的网卡真正联网。 网卡有了、能操作了,但它默认是关着的。得有人:
>
>   把它打开(up)。网卡刚出现时是 administratively down——管理上处于关闭,像一个装好了但没通电开工的设备。要把它 up 起来它才开始工作。你做过这个实验,`ip link set eth0 up`,看到 `state DOWN → UP`,那就是手动把它打开。正常情况这一步该由 networkd 自动做。
>
>   确认有载波(carrier)。 物理世界里,carrier 指网线插着、对端的交换机通着电、线上有信号——也就是"这根线真的连到网络了"。虚拟世界里没有真网线,carrier 表示 hypervisor 把这块虚拟网卡接到了虚拟网络上。你诊断盘里看到的 `CARRIER_STATE=carrier`,就是说这块虚拟网卡的"线"是通的。
>
>   要个 IP 地址。 网卡开了、线也通了,但它还没有地址,没地址就收发不了 IP 包(别人不知道往哪儿发给你)。地址要么你静态写死,要么靠 DHCP——网卡向网络上的 DHCP 服务器喊一嗓子"给我分个地址",服务器回一个。你的配置是 DHCP,最后拿到的 `172.20.197.171` 就是这么要来的。这步需要 udev 做，见下文。
>
>   到这里,sshd 和 gateway 才能通过这块有地址的网卡收发数据。整条正向链是:挂在 PCI 上 → 内核 probe 发现 → 绑驱动(网卡能用了)→ up 打开 → carrier 确认连着 → DHCP 拿到 IP → 程序能收发包。

这条链每一环都得有人负责。在 systemd 这套体系里，分工是这样的：

内核负责最底下两环——probe 出 PCI 设备、绑定驱动（你这次的 virtio_net 是编进内核的，所以这环没问题）。

设备被内核发现之后，它还只是个"裸设备"，得有人把它加工成一块"可用的网卡"：给它确立一个稳定的名字、打上属性（它是哪个驱动、什么类型），然后通知所有关心网卡的程序"有这么一块网卡，已经就绪了"。这道加工工序，systemd 体系交给 udev。

最后，networkd 接手一块被 udev 加工好的网卡，按配置文件去 up 它、发 DHCP、配上地址。

这里有个分工要点，正是它决定了故障的样子：networkd 不直接去问内核要设备，它等 udev 把设备加工好、并发出"就绪"通知，才接手。udev 加工，networkd 配置，两者前后衔接。

## 这次断在哪一环

把上面那条链对照这次的实际情况，断点一目了然。

真根里没装 udev。原因很具体：在 Ubuntu 上，systemd 和 udev 是两个独立的包，镜像的包列表里只写了 systemd，没写 udev。

后果顺着链往下传：网卡被内核 probe 出来了（最底下那环没断），但接下来没人加工它——没确立属性，没发"就绪"通知。等到 networkd 启动、枚举现有网卡，它看到的是一块没加工完的裸设备，于是它的状态机停在 `pending`，不往下走，不去 up、不去 DHCP。表现到最外层，就是 eth0 一直 DOWN、拿不到 IP、SSH 连不上。

那为什么启动早期的日志里明明有 udev 在跑？因为那是 initrd 自带的 udev。回到前面 switch-root 那一句：initrd 是临时系统，切到真根后整套退场，它的 udev 也一起没了。真根是全新一套 systemd，你没给它装 udev，它就真的没有。网卡到了真根里，无人加工。

这么一看，"漏装 udev"就不是一个孤立的意外，而是上面那条网络链里一个逻辑必需的环节被整个拿掉了。理解了这条链，以后任何自定义镜像只要网络不通，排查方向是固定的：沿这条链从下往上，一环一环看断在哪——设备 probe 出来没、驱动绑上没、udev 加工没、networkd 配上没。

至于本体 Ubuntu 为什么一直好好的：它装了完整的 udev（还有 cloud-init、netplan 那套），链是全的。镜像把链砍掉了一环。所以"拿一个正常系统和异常系统比，差异处就是断点"——这次正常和异常之间差的那一样东西，就是 udev。

## 退一层：为什么这次 debug 本身那么费劲

最后补一层，它不属于上面两条因果链，但决定了排查的难度。

debug 的前提是能观测。可这台 TD 上，平时的观测手段几乎都用不了：SSH 不通——而 SSH 不通恰恰就是要查的东西，不能拿它查它自己；VNC 在 TDX 上被禁（它要碰 vCPU 寄存器，跟度量模型冲突）；控制台的 console output 又只能看到固件阶段、还会截断。

所以在能 debug 之前，得先解决一个更前置的问题：造一个不依赖"待修对象"的观测通道。SSH 是待修对象，排除；于是退到一个更底层、不碰网络的通道——让系统启动后把诊断信息直接写进一块裸盘，关机，再从另一个能正常启动的系统（原版 Ubuntu）把那块盘读出来。grub 的一次性引导保证了：就算 verity 镜像启动崩了，下一次也会自动 fallback 回那个能读盘的原版系统。诊断盘 + 一次性引导，合起来才让"在盲盒里跑一次、回来读结果"这个循环转得起来。

>   诊断信息什么时候写：在 rootfs 阶段写的,具体说是真根起到 multi-user 之后,由一个叫 netdiag 的 service 写的。不在 initrd。
>
>   拆开看这个 service 是怎么挂上去、什么时候跑的:
>
>   诊断盘的写入靠 `netdiag.service`,它打在 rootfs 里(overlay 里那份 `netdiag.service` + `netdiag.sh`)。它的依赖写的是 `After=multi-user.target`——意思是排在 multi-user 之后跑。所以时间点是:真根一路启动(sysinit → basic → multi-user)→ 到了 multi-user → netdiag 才执行。整个发生在 switch-root 之后的真根里,initrd 那段早结束了。
>
>   为什么是这个阶段,不是 initrd:你要观测的东西(网卡状态、networkd 日志、各服务起没起)都是真根里的运行时状态。initrd 阶段网卡还没配、networkd 还没正经跑,那时候采集没意义。要看的是"系统正常该联网了它却没联",这个状态只在真根 multi-user 之后才成形。所以诊断盘必须在那个点写,放 initrd 里采不到东西。
>
>   netdiag 具体怎么把数据落到盘上:它不走文件系统,直接 `dd` 写裸盘。脚本里是 `echo "$OUT" | dd of=诊断盘 by-id`——把采集到的文本直接覆盖写到那块盘的前若干 MB。为什么不写成一个普通文件:真根是只读 erofs,写不了文件(这正是 bug 4 踩的——它一开始想往 `/tmp` 写中间文件,失败)。裸盘那块 `…4g` 不在 verity 保护内、是独立的可写块设备,`dd` 直接往上糊就行,绕开了只读根。
